# 五線譜轉簡譜準確度改造設計

日期：2026-10-22
狀態：設計方向已由使用者確認；待審閱本文件後再制定實作計畫。

## 目標

建立可由通用多模態 Agent（包括 Gemini Spark）引導，並可由本專案程式重現及驗證的五線譜轉簡譜流程。優先確保音高、節奏、聲部與歌詞正確；不得以檔案成功輸出代替語義正確性。

## 範圍

### 輸入

- 圖片與 PDF：有 OMR 時可轉成 MusicXML；具視覺能力的 Agent 也可直接建立結構化轉錄。兩種路徑都必須回看來源影像核對，OMR 結果不是正確答案。
- MusicXML（XML、MXL）：直接解析，不經 OCR。

### 輸出

- 簡譜文字（可讀、可核對）。
- 可列印簡譜 PDF。
- 原譜轉錄版 MusicXML（可編輯五線譜，不是非標準的簡譜 MusicXML）。
- MIDI（實際發音音高，供聆聽輔助）。

### 明確不做

- 不新增來源沒有的聲部、旋律、樂句或獨唱頁。
- 不把 Spark 既有產物當成正確答案或黃金標準。
- 不將低信心辨識結果猜補後宣稱完成。

## 架構與資料流程

1. 識別輸入格式及可用工具。
2. 圖片／PDF 使用可用的 OMR 產生 MusicXML，或由視覺 Agent 直接建立結構化轉錄；MusicXML 輸入則直接解析。
3. 轉成共用的正規化 `ScoreModel`。
4. 執行語義驗證，並列出需使用者確認的低信心項目。
5. 依首調或使用者指定的固定唱名產生簡譜事件。
6. 從同一模型輸出簡譜文字、簡譜 PDF、原譜 MusicXML 與 MIDI。
7. 回讀／渲染輸出並比對來源語義，產生驗證摘要。

`ScoreModel` 至少保留：

- 原譜聲部、譜表、小節、拍號、調號、調性／調式、速度與標記。
- 每個音符／休止／和弦的聲部、起拍、時值、記譜音高、實際發音音高。
- 臨時記號與其有效範圍、tie 起止、歌詞音節與延音線關係。
- Pickup、tuplet、裝飾音等會影響時間軸驗證的資訊。
- 來源定位與待確認資訊（頁碼、系統／小節、聲部、候選結果）。

時間值以四分音符拍數表示，允許有理數，避免 tuplets 或複合時值被四捨五入。

## 音高與記譜規則

- 預設採首調：大調主音記 `1`，小調主音記 `6`。
- 使用者指定固定唱名時，採固定 `C=1` 的音高映射，不按調性移動 `1`。
- 以實際發音音高作簡譜映射；移調樂器及八度譜號依來源資訊換算。
- 同時保留原譜記譜音高及移調資訊，使原譜 MusicXML 不因簡譜映射而失真。
- 以來源明確調性資訊及使用者確認為準；調號變更本身不自動判定為轉調。
- tie 驗證比較實際發音音高；跨調後簡譜級數可改變，但不可改變實際連接音高。
- 調性或臨時記號資訊不足時，標記歧義並詢問，不得默認補猜。

## 驗證與失敗處理

### 語義驗證

- 逐聲部依起拍與時值檢查小節時間軸，不將和弦音或重疊聲部當成順序音符累加。
- Pickup、tuplet、裝飾音、延音及不完整終止小節採明確規則處理，不以一般小節總和規則誤判。
- 驗證 tie 兩端的實際音高、時值連續性，以及每個聲部的來源／輸出事件數。
- 歌詞按來源音節關係核對；不可假設每個文字字元都等於一個音符。
- 動態、速度、延長記號及其他已支援來源標記不可無聲遺失。

### 不確定項

- 若 OMR／視覺判讀無法確認，輸出待確認清單，包含來源位置與候選音／時值。
- 未確認前可輸出明確標記為草稿的部分結果，但不得宣稱已完成或全曲準確。
- 若工具、字型或外部 OMR 不可用，說明缺失能力與可交付的部分格式，不得偽稱生成成功。

### 輸出回讀

- MusicXML 解析／輸出 round-trip 比較聲部、音高、起拍、時值、歌詞、調號與拍號。
- MIDI 比較各聲部音符的實際 pitch、start、end；MIDI 僅作輔助核對，不取代來源比對。
- PDF 必須可被轉成頁面影像檢查：無缺字、缺頁、碰撞；多聲部同拍對齊，歌詞與音符位置一致。

## 簡譜 PDF

- 新增 ReportLab 為專用 PDF/vector renderer 依賴。
- 預設 A4 橫向，依拍位排版小節；多聲部使用相同時間座標。
- 文字、音符時值、八度點、增時線、休止、連結符號及標記由結構化事件繪製，不以不可靠 Unicode 音樂字形代替向量圖形。
- CJK 字型需明確設定並檢查字元涵蓋；缺字型或字元時明確失敗，不靜默替代。
- 輸出頁數及聲部數以來源為準，不自動建立獨唱／改編版本。

## Skill 規格

- 採用 Gemini Spark 可載入的標準 YAML frontmatter（`name`、`description`）。
- 指令必須先檢查輸入、可用工具及輸出能力，再執行轉譜與驗證。
- 將首調（小調主音記 `6`）設為預設；明確支援使用者要求的固定唱名。
- 將「不確定先詢問」、「不新增原譜不存在內容」及「只在驗證通過後宣稱完成」列為硬性規則。
- Skill 說明本專案 CLI 的實際支援範圍，不把現有尚未實作的功能描述成已可用；通用 Agent 無工具時須使用誠實降級流程。
- 能讀取影像的 Agent 可進行逐系統視覺轉錄；只有文字能力或無法檢視 PDF 頁面的 Agent 必須要求可讀的 MusicXML／頁面影像，不得假裝已辨識。

## 驗收標準

1. 標準 MusicXML fixtures 的正規化事件與黃金資料完全一致：聲部、實際音高、起拍、時值、休止、tie、歌詞及調性狀態。
2. 首調大調、小調（主音為 `6`）、固定 `C=1`、轉調與臨時記號測試符合明確期望。
3. 跨小節 tie、弱起、和弦／多聲部重疊與 tuplets 不造成拍位或小節驗證錯誤。
4. 輸出聲部數必須等於來源聲部數；不得產生來源不存在的獨唱頁或旋律。
5. PDF 文字與渲染檢查無缺字、明顯碰撞或聲部／歌詞錯位。
6. CLI 與 Skill 的能力聲明一致；缺少外部工具時能清楚報錯或降級。
7. 測試要驗證完整語義，不只檔案存在或輸出含有數字。

## 測試資料與已知限制

- 建立可重現的合成 MusicXML 黃金 fixtures，覆蓋大小調、臨時記號、轉調、tie、pickup、tuplet、SATBB、歌詞與多聲部對齊。
- 使用者提供的《今宵多珍重》原譜 PDF 與 Spark 結果作端到端審查案例。已確認 Spark PDF 多出原需求沒有的「主旋律領唱／獨唱簡譜」頁，這是必須防止的額外生成。
- 目前只有 PDF，沒有已核對的原始 MusicXML 或人工校正事件表；因此此樣本不能單獨充當全曲音高／節奏黃金標準。需要選定人工核對片段，或另提供原始 MusicXML。
- 目前執行環境缺少 `music21`，原測試無法啟動；實作前需在隔離環境安裝專案依賴，再建立可重現的測試命令。
- 圖片／PDF OMR 仍依賴 Audiveris，PDF rasterization 依賴 Poppler；它們不可用時，MusicXML 路徑仍應能獨立測試。
